# Caro Helper - Architecture

Status: prototype (iteration 1, laptop-tested). Last updated 2026-09-16.

## 1. Purpose and scope

Caro works with several web tools daily (Smartsheet, SAP Ariba, two in-house web
apps) plus Excel sheets. Caro Helper is a single-file Windows program that pulls
data from those tools and shows it in a fast local UI, so routine lookups take
seconds instead of minutes of clicking.

Iteration 1 covers Smartsheet only: browse to a sheet or report, view all rows,
search/sort them, copy the result to Excel. Its job is to convince Caro the
approach works, so that she tells us the real questions (PO lookups etc.) that
become predefined queries in iteration 2.

Out of scope for now: Ariba, in-house apps, Excel, writing back to Smartsheet,
caching, auto-update, multi-user.

## 2. Constraints that shaped the design

| Constraint | Consequence |
|---|---|
| Company laptop, no dev tools installed | Single self-contained `.exe`, no runtime, no installer |
| Unsigned `.exe` files are allowed to run, PowerShell policy is `Bypass` | A compiled binary is acceptable; no need for a PowerShell fallback |
| `api.smartsheet.com` reachable directly (verified with `Invoke-RestMethod`) | Plain HTTPS from the app, no proxy handling needed yet |
| Delivery by USB stick | Exactly one file to copy; config lives outside the exe |
| End user is non-technical; the developer sets up once | GUI for all settings; secrets never typed into files |
| Developer works on macOS | Cross-compile; native macOS build for local testing |

## 3. Decisions (ADR-style, short)

**D1 - Go, single static binary.** Cross-compiles from macOS to Windows with one
command, has a built-in HTTP server, `embed` for UI assets, no cgo needed even
for DPAPI (via `golang.org/x/sys/windows`). Rust was the alternative; Go iterates
faster for this size of tool.

**D2 - Local web UI instead of a native GUI or CLI.** The browser is Caro's
daily environment; a web UI gives a good look with zero extra dependencies and
is easy to extend. The exe starts an HTTP server on `127.0.0.1:8765` and opens
the default browser. Console window stays visible as the log/stop mechanism
(close it to quit). Tray icon / hidden mode deferred.

**D3 - React + Vite + Tailwind + shadcn/ui.** Requested for a polished demo;
shadcn's table primitives map directly onto the grid view. Cost: a Node build
step, but only on the dev machine. Vite writes to `cmd/carohelper/dist`, which
Go embeds, so the laptop still receives one file.

**D4 - Smartsheet REST API with a personal access token**, not browser
automation or CSV export. Stable, documented, whole-grid in one call. Token
generated by the user in Smartsheet (Account -> Personal Settings -> API Access).

**D5 - Token stored DPAPI-encrypted in `%APPDATA%\CaroHelper\config.json`.**
Bound to the Windows user; the file is useless on another machine or account.
Non-Windows builds (dev only) fall back to base64 obfuscation and the file is
`0600`. The token is validated against `/users/me` before it is stored.

**D6 - Config outside the exe (`%APPDATA%`), not next to it.** Replacing the
exe from USB never touches the user's settings. `-config <path>` overrides for
tests or a portable setup.

**D7 - Sheets and Reports are both first-class.** Exploration showed that
almost everything Caro uses is a Smartsheet *Report* (rows aggregated from
sheets she cannot see directly). Each configured item has `kind: sheet|report`.

**D8 - Fetch on click, no cache.** Grids are small (tens to hundreds of rows);
one API call takes ~1 s. Filtering and sorting happen in the browser on the full
data set. Revisit if a grid exceeds a few thousand rows.

**D9 - Predefined queries come after the demo.** We do not yet know Caro's real
questions. Iteration 1 ships a generic search box; iteration 2 will add named
queries (initially defined in config by the developer, later editable in the UI).

**D10 - Browser-like User-Agent.** Requests to Smartsheet carry a current
Edge-on-Windows UA (`internal/smartsheet.DefaultUserAgent`), overridable via
`"userAgent"` in config. Motivation: reduce the chance a corporate proxy treats
the tool differently from a browser. If that never matters, switching to an
honest `CaroHelper/x.y` is a one-line change.

**D12 - Smartsheet-like look and multi-source shell.** The UI borrows
Smartsheet's visual language (brand blue, navy navigation, dense bordered grid
with row-number gutter, system font) so it feels familiar, without copying logo
or icons. The shell already anticipates further data sources: an outer icon
rail lists sources (Smartsheet, SAP Ariba, Excel, two in-house web apps; only
Smartsheet is wired), an inner panel lists that source's items, a top bar holds
the avatar menu (account, Settings, Light/Dark). Both navs collapse via a burger
button that keeps its screen position. Nav state and theme persist in
`localStorage`.

**D11 - Exploration tool and data hygiene.** `cmd/explore` dumps workspace /
folder / sheet / report / column structure to `docs/smartsheet-layout.md`.
Structure only (names, ids, column types), never row contents. The dev token
lives in `.env` (gitignored) and is read only by the explore tool; the app never
reads `.env`.

## 4. Components

```
+-----------------------------+        +-----------------------------------+
|  Browser (Edge)             |  HTTP  |  carohelper.exe                   |
|  React SPA                  | <----> |  internal/server  JSON API + SPA  |
|  - source rail + sheet panel|        |  internal/config  %APPDATA% json  |
|  - Grid page (search/sort)  |        |  internal/smartsheet REST client  |
|  - Settings (avatar menu)   |        |                                   |
+-----------------------------+        +----------------+------------------+
                                                        | HTTPS + Bearer token
                                                        v
                                               api.smartsheet.com/2.0
```

| Package | Responsibility |
|---|---|
| `cmd/carohelper` | Entry point. Flags, config load, listen on loopback, open browser, embed `dist/`. |
| `cmd/explore` | Dev tool. Reads `.env`, prints Smartsheet structure as Markdown. Flags: `-workspace`, `-sheet`, `-report`, `-reports`, `-no-columns`. |
| `internal/smartsheet` | Minimal API client: `Me`, `ListWorkspaces`, `GetWorkspace` (full tree), `GetSheet`, `GetReport`. Pagination, typed errors (`APIError`), report column-id normalisation. `SMARTSHEET_BASE_URL` env override for tests. |
| `internal/config` | `Store` over `config.json`: sheets/reports aliases, port, user agent, protected token. Platform-specific `protect`/`unprotect` (`protect_windows.go` DPAPI, `protect_other.go` fallback). |
| `internal/server` | HTTP routes, request logging, error mapping, `SheetView` flattening (hidden columns removed, cells keyed by column id), parallel workspace browse (4 concurrent), SPA fallback handler. |
| `frontend` | React SPA. `lib/api.ts` typed client; `pages/SettingsPage.tsx` (token, alias list, collapsible workspace tree); `pages/SheetPage.tsx` (Smartsheet-style grid, live AND-search, sort, copy TSV); `App.tsx` (hash routing `#/<source>/sheet/<id>`, `#/settings`; source rail, sheet panel, top bar with avatar menu, burger collapse, dark mode). |

## 5. HTTP API (loopback only)

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/status` | `{hasToken, tokenValid, user, configPath, tokenError?}`; validates token live via `/users/me`. |
| PUT | `/api/token` | `{token}` -> verifies with Smartsheet, stores encrypted. 401 if rejected. |
| GET | `/api/sheets` | Configured aliases `[{alias, kind, sheetId}]`. |
| PUT | `/api/sheets` | Replace the alias list (validated). |
| GET | `/api/grid/{kind}/{id}` | Full grid as `SheetView`; `kind` is `sheet` or `report`. |
| GET | `/api/browse` | All workspaces with nested folders, sheets, reports. |
| GET | `/*` | SPA (static assets, `index.html` fallback). |

Errors are `{error: string}` with 400/401/404/500. Smartsheet 401/403 map to 401.

`SheetView`:

```json
{
  "id": 1, "name": "...", "permalink": "...", "modifiedAt": "...", "totalRows": 57,
  "columns": [{ "id": 1, "index": 0, "title": "PO", "type": "TEXT_NUMBER", "primary": true, "options": [] }],
  "rows": [{ "id": 10, "rowNumber": 1, "cells": { "1": "4711" } }]
}
```

Cells hold display strings only; empty cells are omitted.

## 6. Configuration file

`%APPDATA%\CaroHelper\config.json` (macOS: `~/Library/Application Support/CaroHelper/config.json`)

```json
{
  "tokenEnc": "<base64 DPAPI blob>",
  "sheets": [
    { "alias": "MedChem VERS", "kind": "report", "sheetId": 1732057421008772 }
  ],
  "port": 8765,
  "userAgent": ""
}
```

Created on first run. `kind` defaults to `sheet` when missing (backwards
compatibility with the first prototype).

## 7. Security notes

- Server binds to `127.0.0.1` only; nothing is reachable from the network.
- No authentication on the local API: any local process could call it. Accepted
  for a single-user laptop tool. If that ever matters, add a per-run random
  token passed to the SPA.
- Token never appears in logs, URLs, or API responses (`/api/status` only reports validity).
- Token is validated before persisting, so a typo never gets stored.
- Read-only against Smartsheet; the app performs GET requests only.
- `.gitignore` excludes `.env`, `*.exe`, build output. `docs/smartsheet-layout.md`
  contains structure only.

## 8. Build and delivery

```
make build-win   # npm build -> cmd/carohelper/dist -> GOOS=windows go build -> dist/carohelper.exe
make build       # same, native binary for local testing
make explore     # go run ./cmd/explore > docs/smartsheet-layout.md
go test ./...    # unit tests (currently: UA header behaviour)
```

Binary is ~8 MB, statically linked, `CGO_ENABLED=0`, stripped. Copy
`dist/carohelper.exe` to the laptop via USB. Updates are the same copy; config
is untouched.

Frontend dev loop: `cd frontend && npm run dev` (Vite proxies `/api` to
`localhost:8765`) alongside `go run ./cmd/carohelper -no-browser`.

## 9. Findings from the Smartsheet exploration

- The account is a shared mailbox (`emea-esc-sub-region.at_de@...`), not
  Caro's personal user; visibility follows that account's permissions.
- ~12 workspaces: one per customer and year (`2025/2026 ESC Workspace - BI BC`,
  `BI OX`, `BI ING`, `Pfizer`, `Sandoz/Novartis`, `Teva/GRT/BioNTech/Elanco`,
  `BioNTech Marburg`).
- Nearly all leaf items are **Reports**, grouped in folders per lab area
  (`LEAN MedChem`, `LEAN AD`, `LEAN ADB`, `LEAN BPAD`, `LEAN BPQC`, `CLAMP`).
  Per area: `Forecast`, `awaiting customer confirmation`, `ready to schedule`,
  `VERS`, `UFP` (some also `Serviceberichte`).
- Workspace-level reports encode a status pipeline: `03 - Ready to Schedule`,
  `03 - Wait for Appointment`, `04 - Scheduled`, `05 - Wait for Service Report`,
  `07 - Wait Supplier Invoice`, `09 - Done`, `11 - Ready to Invoice`,
  `12 - Escalated to Sourcing`, `13 - Escalations SCC ...`.
- PO-relevant columns seen: `Service Provider PO`, `Contract PO Customer`,
  `BPO`, `Service Contract ID`, `Scheduled Service SO Number`,
  `Agency Forecast Price`, `Preisfreigabe` (checkbox), `SSM - Quote Expiry Date`,
  `Next Scheduled PM/OQ/Cal Date`.
- Report columns expose only `virtualId`; cells carry both `columnId` (source
  sheet) and `virtualColumnId`. The client normalises onto the virtual id.
- Full workspace browse costs ~1 API call per workspace (~8 s with 4 in parallel).

Full dump: `docs/smartsheet-layout.md`.

## 10. Roadmap (not committed, in likely order)

Done: laptop verification (exe runs, token stored via DPAPI, browser opens).

1. Collect Caro's recurring questions; add **predefined queries** (named
   filters on a grid: column/operator/value, initially in config).
2. Cross-grid PO lookup: type a PO number once, search across all configured
   reports.
3. Column chooser and per-user column order; remember last search per grid.
4. Excel: read local sheets (likely via an `.xlsx` library in Go) and join with
   Smartsheet data.
5. Ariba and in-house web apps: evaluate APIs vs. export files vs. automation.
6. Quality of life: tray icon / no console, version display, self-check page.
